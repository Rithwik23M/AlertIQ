# AlertIQ  -  Model Risk Architecture

**Document type:** Model risk framework  
**Milestone:** 2.1 (preparation for Milestone 3)  
**Status:** DRAFT  -  defines evaluation extensions required before any production deployment  
**Created:** 2026-09-12

---

## 1. Purpose

This document identifies the evaluation extensions, monitoring controls, and governance requirements that must be addressed before AlertIQ can be deployed to support real AML operations. It is not a deployment checklist  -  it is a risk register that defines the *scope of Milestone 3*.

The simulator results (AUC-ROC 0.979, Recall@20% ≥ 0.70) reflect a constructed dataset where SAR-predictive signals are embedded by design. These numbers are **not transferable claims** about real TMS performance. A regulator, risk officer, or validation team would reject a deployment package that cited these figures without external validation evidence.

---

## 2. Model Risk Dimensions

### 2.1 External Validation (CRITICAL  -  blocks any deployment)

**Gap**: All evaluation to date is on simulator data generated by the same team that built the model. No independent validation exists.

**Required before deployment**:
- Evaluation on at least one real TMS alert export (de-identified)
- Comparison against institution's existing manual prioritisation method as baseline
- Holdout period ≥ 3 months to test temporal stability
- SAR filing confirmation delay tracking (labels may arrive 30–90 days after alert)

**Acceptance threshold on real data**: To be negotiated with institution risk committee. A reasonable starting target is Recall@20% ≥ 0.55 with AUC-ROC ≥ 0.70, but the institution's current analyst recall rate is the meaningful baseline.

---

### 2.2 Multi-Window Temporal Evaluation

**Gap**: Current evaluation uses a single train/val/holdout split (60/20/20 by row count). One holdout window cannot distinguish trend from variance.

**Required**: Rolling-window back-test across at least 3 non-overlapping evaluation periods.

```
Period 1: Train Jan–Mar, Evaluate Apr
Period 2: Train Jan–Apr, Evaluate May  
Period 3: Train Jan–May, Evaluate Jun
```

**Metrics to track across windows**:
- Recall@20% variance (σ < 0.05 is a reasonable stability target)
- AUC-ROC trend (declining trend signals distribution shift)
- Selected threshold drift (> 0.05 shift between windows requires investigation)
- Calibration error (Expected Calibration Error per window)

**Failure criterion**: Any window where Recall@20% < 0.45 (M2 acceptance floor) triggers mandatory review before deployment.

---

### 2.3 Distribution Shift Detection

**Gap**: The model assumes the alert population distribution at inference time resembles the training distribution. TMS rule changes, typology emergence, and macroeconomic shocks can break this assumption silently.

**Required monitoring controls**:

| Signal | Monitoring Method | Alert Threshold |
|--------|------------------|-----------------|
| Feature distribution shift | Population Stability Index (PSI) per feature | PSI > 0.25 on any top-5 feature |
| Score distribution shift | KS test: daily production scores vs. training scores | p < 0.01 |
| SAR rate change | 7-day rolling SAR rate vs. 90-day baseline | ± 3σ deviation |
| Recall proxy | Analyst feedback: SARs found outside top-20% queue | > 10% of filed SARs |

**Implementation note**: PSI and KS monitoring require production score logs. These must be stored at inference time, not reconstructed post-hoc.

---

### 2.4 Threshold Stability Analysis

**Gap**: The F1-optimal threshold (currently ~0.115) is selected on the validation split. Its sensitivity to training data composition has not been quantified.

**Required before deployment**:

1. **Bootstrap threshold variance**: Resample the training set 100× with replacement; fit 100 models; record threshold distribution. If σ > 0.03, threshold selection is unstable and requires a more robust objective.

2. **Threshold objective review**: F1 optimisation is a reasonable default, but AML operations typically prefer:
   - *Recall-constrained*: Fix minimum recall ≥ 0.90, minimise FPR  -  appropriate when missing SARs has higher regulatory cost than false investigations
   - *Cost-utility*: `cost = FN × cost_missed_sar + FP × cost_false_investigation`  -  requires institution to supply cost estimates
   - *Capacity-aligned*: No threshold needed; primary operating mode is capacity-ranking (already implemented)

3. **Threshold drift monitoring**: Track selected threshold across retraining cycles. Drift > 0.05 per cycle requires root-cause analysis.

---

### 2.5 Calibration Assessment

**Gap**: AlertIQ reports raw HistGBM probabilities as scores without calibration. GBDT models are typically well-calibrated but this should be verified before the scores are used for cost-utility thresholding.

**Required**:
- Reliability diagram (actual SAR rate vs. predicted probability, decile-binned)
- Expected Calibration Error (ECE): acceptable if ECE < 0.05
- Brier Score as supplementary ranking quality metric (lower = better)

**If poorly calibrated** (ECE ≥ 0.05): Apply isotonic regression or Platt scaling calibration layer on the validation set. Re-evaluate calibration on holdout.

---

### 2.6 Typology-Level Performance

**Gap**: Aggregate Recall@20% masks potential blind spots at the typology (TMS rule) level. A model that achieves 95% recall on structuring alerts while missing 70% of jurisdiction-risk alerts is not uniformly effective.

**Required breakdown**:

| Rule Group | Description | Recall@20% |
|------------|-------------|------------|
| Cash structuring (R01, R02) | High-frequency, distinct signal | to be computed |
| Velocity anomalies (R03, R04) | Ratio features  -  model strength area | to be computed |
| Jurisdiction risk (R05, R08) | Flag features  -  potential weakness | to be computed |
| Shell counterparty (R09, R11) | Rare  -  small sample, high variance | to be computed |
| PEP/adverse media (R12, R13) | Low base rate  -  calibration sensitivity | to be computed |

**Acceptance criterion**: No rule group with ≥ 50 holdout SARs should have Recall@20% < 0.40. Rule groups below this floor require feature engineering investigation.

---

### 2.7 Account-Level Blind Spots

**Gap**: The error analysis identifies accounts with frequent false negatives, but does not characterise whether these represent structural model failures (the account's typology is underrepresented in training) or genuine edge cases.

**Required analysis**:
- Identify top-10 accounts by FN count in holdout
- Compute feature-space distance from training set centre for these accounts (Mahalanobis distance)
- If FN accounts are > 2σ from training distribution: they represent out-of-distribution accounts  -  the model cannot be expected to generalise

**Account-level monitoring in production**: Track per-account alert score history. Accounts where model score trend diverges from eventual SAR outcome should be flagged for manual review.

---

### 2.8 Fairness and Adverse Impact

**Gap**: The simulator does not include demographic attributes, so this cannot be evaluated on simulated data. For real deployment:

- Define sensitive attributes consistent with applicable law (jurisdiction-specific)
- Measure false positive rate disparity across alert segments (e.g., by account tenure, customer segment, geography)  -  not protected-class attributes, but structural proxies
- Document that the model does not amplify existing investigative bias

**Minimum requirement**: Documented policy on which attributes were considered, why the model does not use them directly, and how indirect discrimination through correlated features is addressed.

---

### 2.9 Model Governance and Change Control

**Required governance controls before any live operation**:

| Control | Requirement |
|---------|-------------|
| Model inventory | AlertIQ registered in institution model inventory with version, owner, purpose |
| Independent validation | Validation team separate from development reviews model documentation and test results |
| Explainability | For every analyst alert, a human-readable score explanation (top-3 feature contributions) must be available on demand |
| Override mechanism | Analyst can manually escalate any alert irrespective of model score; overrides are logged |
| Retraining schedule | Model retrained at minimum quarterly; triggered earlier by PSI > 0.25 alert |
| Rollback procedure | Previous model version available for immediate deployment; rollback criterion defined in advance |
| Audit log | Every model score, threshold applied, and analyst action logged with timestamp |
| SLA | Model inference latency ≤ 200ms at p99 for live scoring; batch refresh ≤ 4 hours |

## 3. Milestone 3 Scope (derived from this document)

Based on the gaps above, Milestone 3 should implement the following in priority order:

**P0  -  Blocks any real-data evaluation**:
1. Rolling-window back-test engine (§2.2)
2. Score calibration layer + calibration metrics (§2.5)
3. Typology-level performance breakdown in `Evaluator` (§2.6)

**P1  -  Required before pilot deployment**:
4. Distribution shift monitoring: PSI and KS per feature (§2.3)
5. Threshold bootstrap variance analysis (§2.4)
6. Account-level FN characterisation with Mahalanobis distance (§2.7)

**P2  -  Required before full deployment**:
7. Explainability: SHAP values for per-alert score breakdown (enables §2.9 override mechanism)
8. Fairness audit framework (§2.8)
9. Production monitoring dashboard (§2.3 + §2.9)

**Out of scope for Milestone 3**: External validation on real data (requires institutional data access), model inventory registration (institutional process), independent validation team (human process).

## 4. Claim Correction Summary

The following claims from the Milestone 2 experiment results are **not deployment claims**:

| Claimed result | Correct framing |
|----------------|-----------------|
| AUC-ROC = 0.979 | On simulator data with engineered signals. Expected to be 0.70–0.85 on real noisy TMS data after proper validation. |
| Recall@20% ≥ 1.00 | On simulator holdout. May degrade significantly on real data; target on real data TBD. |
| "Outperforms severity baseline by +Δ" | Meaningful only after real-data comparison against institution's actual prioritisation method. |

All public-facing documentation must carry this framing. Citing simulator AUC as expected production performance would be a model risk violation.
